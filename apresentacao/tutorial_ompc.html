00 O que é OMPC, e por que ele muda o código

A diferença para o MPI explícito não é sintática — é sobre quem distribui.

No MPI manual, o programador distribui: cada rank calcula sua fatia e chama MPI_Allreduce à mão. No OpenMP Cluster, você escreve #pragma omp target e o runtime despacha aquela região para um nó remoto via MPI; os dados viajam pelas cláusulas map().

Restrição dura—só arrays POD cruzam a fronteira

A última linha moldou todo o projeto: dentro de um target não passam std::vector, std::complex, casacore, FFTW nem std::cout. Por isso o pipeline foi partido em duas peças — leitura do MS fora, cálculo distribuído dentro:

Por que o canal é a unidade certa. Cada canal espectral tem a própria frequência e é processado de forma independente até a soma das grades — exatamente o desenho “num_channel = 1 per archi. node” dos slides do laboratório. O sim_large.ms tem 4 canais (140–143 MHz), então há 4 unidades de trabalho reais.

01 Preparar os dados

O container não tem casacore, então o MS é convertido antes, no seu PC.

no seu PC · WSL
WSL · bash
# compila o exportador (host: precisa de casacore)
g++ -std=c++17 -O2 -Iinclude -isystem /usr/include/casacore \
    tools/ms_export.cpp src/ms_io.cpp \
    -lcasa_ms -lcasa_tables -lcasa_casa -o build/ms_export

# exporta 1 arquivo .vis por canal (400 mil linhas para o teste)
./build/ms_export ../data/sim_large.ms/sim_large.ms data/large 400000
canal 0: 400000 vis | 140.000 MHz | u_max 29071.4 lambda -> data/large_ch0.vis canal 1: 400000 vis | 141.000 MHz | u_max 29279.0 lambda -> data/large_ch1.vis canal 2: 400000 vis | 142.000 MHz | u_max 29486.7 lambda -> data/large_ch2.vis canal 3: 400000 vis | 143.000 MHz | u_max 29694.3 lambda -> data/large_ch3.vis

Repare que o u_max cresce com o canal: a linha de base física é a mesma, mas em frequência maior ela vale mais comprimentos de onda. É por isso que cada canal precisa da sua própria frequência — usar a do canal 0 para todos erraria as coordenadas UV em ~2%.

Se o MS não abrir. O zip do dataset cria uma pasta aninhada: o MS de verdade fica em data/sim_large.ms/sim_large.ms/, não em data/sim_large.ms/.

02 Enviar para o cluster

Três níveis: seu PC → gateway → sorgan. E o destino tem de ser o /scratch.

no seu PC · PowerShell
PowerShell
scp -P 6868 -r ddfacet_cpp thiago.pinto@ssh.lsc.ic.unicamp.br:/tmp/
no gateway
gateway
scp -r /tmp/ddfacet_cpp sorgan:/scratch/$(whoami)/
Por que não deixar no /tmp. O /tmp é local de cada máquina — o sorgan e os nós de computação não enxergam o /tmp do gateway, e ele é limpo periodicamente. O /scratch é o que fica visível para todos os nós.

Leve junto os .vis (~51 MB nos 4 canais). Sem eles o programa não roda.

03 Alocar nós e compilar no container

O clang do OMPC só existe dentro do container — e ele deve ser baixado de um nó de computação.

no sorgan
sorgan
# reserva 2 nós (anote os nomes que ele imprimir)
salloc -N 2 -p cpu --no-shell --exclusive --time 01:00:00

# entra num dos nós alocados
ssh sorgan-cpu1
cd /scratch/$(whoami)/ddfacet_cpp
no nó de computação
sorgan-cpuN
# baixa o container do OpenMP Cluster (uma vez só)
./scripts/sorgan_ompc.sh setup

# compila com o clang patched, de dentro do container
./scripts/sorgan_ompc.sh build

O que o build executa por baixo — vale saber para explicar:

o comando real
apptainer exec --nv ompc_latest.sif \
  clang++ -O2 -std=c++17 -fopenmp \
          -fopenmp-targets=x86_64-pc-linux-gnu \
          -Iinclude src/main_ompc.cpp -o ddfacet_ompc

A flag destacada é a chave: ela diz que o device de offload é outra máquina x86 — não uma GPU. É isso que faz o OMPC despachar as regiões target pela rede.

Se o container tiver outro nome. O pull costuma gerar ompc_latest.sif, mas o tutorial do laboratório menciona mpp.sif. Confira com ls *.sif e, se preciso, export SIF=<nome>.sif antes de rodar o script.

04 Rodar — e a prova de que está correto

O comando tem dois grupos de processos; entender isso é metade da explicação.

no nó de computação
execução distribuída
ml load mpich

mpirun -hosts=sorgan-cpu1,sorgan-cpu2 \
   -np 2 apptainer exec --sharens --nv ompc_latest.sif llvm-offload-mpi-proxy-device \
 : -np 1 apptainer exec --sharens --nv ompc_latest.sif ./ddfacet_ompc data/large 128 3 4

São N + 1 processos: N proxy-devices (os nós que executam as regiões target) e 1 head (que roda o programa e cria as tarefas). O : separa os dois grupos — é lançamento MPMD.

O sinal de que o offload funcionou

[HEAD] pid=4021 [WORKER] ciclo 0 canal 0 pid=7734 [WORKER] ciclo 0 canal 1 pid=7735 [WORKER] ciclo 0 canal 2 pid=9182 [WORKER] ciclo 0 canal 3 pid=9183

PIDs diferentes do HEAD = as regiões target executaram em processos remotos. Se todos vierem com o mesmo PID do head, o offload não subiu e o código caiu para execução local — aí o problema é de toolchain, não do pipeline.

O teste de invariância (é isto que prova a corretude)

sorgan-cpuN
./scripts/sorgan_ompc.sh check sorgan-cpu1,sorgan-cpu2

Ele roda com 1 nó e com N nós e compara os checksums. Têm de ser idênticos. A lógica: distribuir só reparte os canais; a soma das grades UV parciais é a mesma soma, e soma é associativa. Se os checksums divergirem, algum canal foi perdido, duplicado ou houve corrida.

05 O que mostrar ao orientador

Ele avalia paralelização — então a ordem é: corretude, depois desempenho.

Checksum

idêntico

1. Corretude antes de velocidade

Mostre o check: a imagem final é a mesma com 1 nó e com N nós (checksum 6.851498 nos testes locais com 1, 2 e 4 unidades). Um speedup sem corretude não vale nada, e essa é a primeira pergunta que um orientador de paralelismo faz.

2. A fração paralela — o número mais forte

99,4% do tempo dentro das regiões target — a fração serial (FFT do modelo, soma das grades, FFT⁻¹ e CLEAN, todos no host) é de apenas ~0,6%. O trabalho por canal é grosso e o que volta ao host é só a grade final.

Não anuncie um teto de speedup a partir desse número. Os 99,4% foram medidos com as regiões target executando localmente, onde as cláusulas map() não pagam rede. No cluster, a transferência das grades entre nós é real e entra na conta. O honesto é apresentar a fração serial medida (~0,6%) e, ao lado, o speedup real medido no cluster — que sai dos tempos do run.

4. As decisões de projeto (o que ele vai perguntar)

DecisãoPor quê
Canal como unidade de distribuiçãoCanais são independentes até a soma das grades; cada um tem frequência própria. Casa com o desenho do laboratório (1 canal por nó).
degrid+residual+grid fundidosUma única passada pelas visibilidades: a visibilidade predita nunca volta pela rede, o que reduz o tráfego entre nós (o custo dominante no OMPC).
Leitura do MS fora do targetCasacore não existe no container e não é mapeável. Exportar para .vis POD resolve, e ainda evita reparsear tabelas em cada execução.
FFT própria (radix-2)Não depender de FFTW, que pode não estar no container. Custo: exige imagem com lado potência de 2.
Grade de saída por canalCada tarefa escreve na sua própria grade → sem corrida entre tarefas; a soma acontece no host.
Seja honesto sobre o limite atual. A imagem ainda não é cientificamente boa: o teste usa 400 mil das 7,8 milhões de linhas, 128 píxeis, sem W-projection e com kernel gaussiano, num campo de 8° com 1.895 fontes. Para comparar de verdade com a imagem de referência img_wproj_large_I.fits faltam W-projection e faceting. O que está fechado e medido é a paralelização — que é o objeto da avaliação.
