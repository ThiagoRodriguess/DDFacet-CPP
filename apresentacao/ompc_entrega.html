01 A ideia central

Uma sugestão de organização de código virou a chave da paralelização multi-nó.

A revisão pediu que o canal espectral deixasse de ser fixo em zero e virasse um parâmetro explícito, antecipando o processamento no OpenMP Cluster. Ao implementar isso, ficou evidente que o canal é a unidade natural de trabalho distribuível: cada canal tem frequência própria e é processado de forma independente até a soma final das grades.

É o desenho “um canal por nó da arquitetura”. Hoje o pipeline faz exatamente isso:

02 As três alterações, com evidência

Cada uma implementada, compilando e verificada em execução.

1 Canal como parâmetro explícito

A leitura do MS passou a receber o canal, e ele se propaga até a configuração do pipeline.

ms_io.cpp
// antes: sempre o canal 0
const Complex c = data(0, 0, i);

// agora: canal explícito — e a FREQUÊNCIA vem do mesmo canal
const double freq = cf(IPosition(1, channel));   // CHAN_FREQ[channel]
const double wl   = C_LIGHT / freq;              // muda o λ!
const Complex c   = data(0, channel, i);

Um detalhe físico que vale destacar: trocar de canal muda a frequência e, portanto, o comprimento de onda que converte UVW de metros para comprimentos de onda. Usar CHAN_FREQ[0] para todos os canais produziria coordenadas UV erradas. A execução confirma o efeito:

canal 0: 140.000 MHz | u_max 29071.4 lambda canal 1: 141.000 MHz | u_max 29279.0 lambda canal 2: 142.000 MHz | u_max 29486.7 lambda canal 3: 143.000 MHz | u_max 29694.3 lambda

Mesma linha de base física; em frequência maior ela vale mais comprimentos de onda — variação de ~2% entre o primeiro e o último canal.

2 Termo-w na mudança de centro de fase

O w era lido do MS e ignorado no cálculo. Agora entra na fase de cada faceta.

ddfacet.cpp · degrid
const double lm2  = l0*l0 + m0*m0;
const double n0m1 = (lm2 < 1.0) ? (sqrt(1.0 - lm2) - 1.0) : 0.0;

// fase da faceta, agora com o termo-w
const double ph = -2.0*PI * (u[k]*l0 + v[k]*m0 + w[k]*n0m1);

No grid aplica-se a mesma fase com sinal oposto, preservando a relação adjunta entre os dois operadores. Para a faceta central (l₀=m₀=0 → n₀=1) o termo se anula, como esperado. A guarda contra l₀²+m₀² ≥ 1 evita raiz de número negativo em facetas muito afastadas.

Ainda não é W-projection completa — é a aproximação coerente que faz o w lido ter efeito real no cálculo.

3 DDE — ganho dependente da direção

Versão escalar do formalismo RIME/Jones: um ganho complexo por faceta, aplicado como ×G no degrid e ×conj(G) no adjunto.

degrid / grid
// struct Facet
std::complex<double> directional_gain;   // padrão (1,0) = identidade

// degrid: aplica o ganho
acc *= gain;

// grid (adjunto): aplica o conjugado — preserva a relação adjunta
dv_k = res.data[k] * phase * conj(gain);

Verificação em execução. Com os ganhos ativados, a recuperação de fluxo degrada apenas nas facetas fora do centro — que é o efeito físico esperado, já que a deconvolução não conhece os ganhos:

FonteFluxo verdadeiroSem DDECom DDE
centro (faceta 0, G = 1)1,0000,999 · 100%0,997 · 100%
faceta 1 (arg G = 0,15 rad)0,7000,699 · 100%0,628 · 90%
[DDE] ganhos direcionais G_i ATIVOS (4 facetas): faceta 0: |G|=1.0000 arg(G)=0.0000 rad faceta 1: |G|=1.0000 arg(G)=0.1500 rad faceta 2: |G|=1.0000 arg(G)=0.3000 rad faceta 3: |G|=1.0000 arg(G)=0.4500 rad

A faceta central, cujo ganho é a identidade, fica intacta. Isso demonstra que o ganho está genuinamente conectado nos dois operadores — e não apenas declarado.

Por que o ganho é determinístico. Gi é função apenas de (l₀, m₀) e do índice da faceta, nunca aleatório. Se fosse aleatório, cada nó geraria um valor diferente e o resultado passaria a depender do número de nós — quebrando a propriedade que usamos como prova de corretude. Por padrão G = (1,0), então nada do que já estava validado muda.

03 O pipeline em OpenMP Cluster

Ciclo completo do Algoritmo 1, com o trabalho pesado distribuído por canal.

A diferença para o MPI explícito não é sintática: no MPI o programador distribui e chama MPI_Allreduce à mão; no OMPC o runtime despacha cada região target para um nó e move os dados pelas cláusulas map().

main_ompc.cpp · núcleo
#pragma omp parallel
#pragma omp single
{
  for (int c = 0; c < nchan; ++c) {
    #pragma omp target nowait                       \
        depend(out: grp[0:ngi])                       \
        map(to: up[0:nv], vp[0:nv], wp[0:nv], ...)    \
        map(tofrom: grp[0:ngi], gip[0:ngi])
    {
      ompc_degrid_residual_grid(...);   // executa em NÓ REMOTO
    }
  }
  #pragma omp taskwait
}

Duas restrições que moldaram o projeto

Restrição do container OMPCComo foi resolvida
Só arrays POD cruzam a fronteira do target — nada de std::vector, std::complex ou casacoreKernel reescrito sobre arrays planos, com complexos como pares re/im; leitura do MS movida para fora (ms_export gera um .vis por canal)
Não se pode contar com FFTW dentro do containerFFT própria, radix-2 iterativa, sem dependência externa (custo: lado da imagem potência de 2)

O degrid, o cálculo do resíduo e o gridding foram fundidos numa única passada pelas visibilidades: assim a visibilidade predita nunca retorna pela rede, reduzindo o tráfego entre nós — que é o custo dominante no OMPC.

Escalabilidade

Cada canal é despachado como uma tarefa independente. Medindo o tempo das tarefas com 1, 2 e 4 unidades de execução, sobre os mesmos 4 canais:

UnidadesTempo das tarefasSpeedupEficiência
113,6 s1,00×—
26,7 s2,03×102%
43,6 s3,79×95%

Escalamento praticamente linear — esperado, já que os canais são independentes até a soma final das grades e a fração serial (FFT do modelo, soma, FFT⁻¹ e deconvolução) é pequena diante do gridding.

O que estes números são — e o que não são. Foram medidos com as regiões target executando em threads da mesma máquina (memória compartilhada), porque o compilador do OpenMP Cluster ainda não pôde ser usado — o cluster está em manutenção. Eles demonstram que a decomposição por canal escala, mas não incluem o custo de rede entre nós. O speedup multi-nó real só pode ser afirmado depois de medido no cluster, com o mesmo código-fonte.

Detalhe de implementação que essa medição expôs: #pragma omp target nowait apenas permite execução diferida — sem device de offload, o compilador a executa inline e tudo sai sequencial. Envolver cada região numa #pragma omp task explícita garante a assincronia nos dois cenários: threads distintas no host, nós distintos no cluster.
